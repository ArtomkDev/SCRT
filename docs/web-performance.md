# Dashboard performance

Run `corepack pnpm benchmark:web` for a local synthetic benchmark with 100,000 members, 250 mapped roles and 1,000 concurrent consumers. It measures indexing, searching, grouping and database fan-out without credentials or external requests. Results depend on local CPU load; this is not a production HTTP capacity test.

Reference local run on 2026-09-30: index construction 36.81 ms, search 38.38 ms, role grouping 9.83 ms, concurrent read coalescing 0.27 ms and listener fan-out 1.33 ms. The 1,000 consumers produced one upstream read and one upstream listener. All 144 workspace tests, typecheck, lint and production build passed. A local production HTTP smoke check covered the server pages, all Voice tabs and access control without a session; protected pages redirected and all five member endpoints returned 401. Authenticated production latency and browser interaction remain unmeasured.

Navigation prefetches a complete route on hover, keyboard focus or touch. Dynamic and prefetched page segments remain in the browser router cache for 30 seconds. Live events and server-action revalidation refresh the dashboard. Guild layouts stream a loading state while authorization resolves; each protected page and operation still checks authorization.

Discord roles and channels use the existing guild/resource-revision caches. Access-control guild metadata is cached for 30 seconds; displayed member profiles for 60 seconds, keyed by guild, member and directory revision. These caches serve presentation only. Ownership, membership and access mappings used by mutations remain live. Concurrent Firestore reads share an in-flight request and discard the result after completion; no permission decision is cached across requests.

Authorization no longer calls OAuth `GET /users/@me/guilds/{guildId}/member` on navigation or server-list subscriptions. That endpoint's cooldown previously prevented settings and the server list from loading. Necessary role checks now use the bot's `GET /guilds/{guildId}/members/{sessionUserId}` endpoint with request-scoped deduplication only. The server list first checks live guild membership plus direct or `@everyone` grants, avoiding member requests even when other role mappings exist. Protected pages still resolve the complete permissions from live roles; revoked membership/roles and upstream failures never fall back to cached profile data. Regression tests exercise the actual permission policy with an unavailable OAuth member endpoint, mixed grants, role removal, missing membership and bot API errors. Authenticated browser verification remains outstanding because the browser tool failed to start its Windows sandbox.

Member snapshots fetch at most one page when the client requests it, with 1,000 Discord members per page. Client cancellation stops further pages. The server member-page cache is bounded to 80 pages and 32 distinct pending loads, with a 120-second TTL and keys including bot credential fingerprint, guild, directory revision and cursor. Concurrent consumers of the same page share one Discord call. A changed revision selects a new cache entry.

The client displays pages progressively, batches updates, deduplicates member IDs and replays contiguous live changes received during loading. Missing revisions or reset events trigger a bounded retry with backoff. Search works while the first pages arrive and retains only the best 30 matches. A normalized search index is reused between keystrokes. Role grouping uses role ranks instead of scanning every mapped role for each member.

Visible member directories check their revision every five minutes and only reload when needed, with a full reconciliation at least every 15 minutes to cover missed Gateway events. Hidden tabs close their event connections; reconnects use backoff and jitter. Firestore listeners are shared per database and document/query, including overlapping dashboard and member streams. The last subscriber releases its listener and retained snapshot. Slow SSE clients disconnect before their event queue exceeds 64 KiB.

Discord requests have bounded queues (512 requests in total, 64 on one route), a 10-second queue timeout, a 30-second total request budget and an eight-second network timeout per attempt. Reasonable `Retry-After` values are honored; excessive cooldowns fail without an early retry. A timed-out waiter cannot let later requests overtake the active request.

Memory caches, listener sharing and request coalescing operate within each process. Multiple Railway replicas each maintain their own instances. Real capacity and first-load latency still depend on Discord/Firebase latency, API quotas, replica count, memory and CPU; measure authenticated production traffic before promising a concurrent-user limit.
