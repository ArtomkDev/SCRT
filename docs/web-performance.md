# Dashboard performance

The 2026-10-04 audit and measurements are recorded in [the project audit](project-audit-2026-10-04.md). Hidden/offline tabs pause live connections and timers; returning to the page coalesces pending work into one refresh. Concurrent refreshes are serialized and background updates use a React transition. Period changes retain mounted content while the next response loads. Route loading states preserve headings, cards and tabs, and animate only content values. Member snapshot requests and revision polls are abortable and do not overlap on resume. These behaviors have regression tests; long-idle authenticated production browser timing still requires live acceptance.

A broken compressed RSC stream can fail after the router has already accepted its first chunk. The global error boundary recovers recognized client network errors through a fresh document load, at most once per minute per tab. It waits until the tab is visible and online; server errors with a digest, programming errors and intentional aborts do not trigger automatic recovery. A manual reload remains available, including when sessionStorage is blocked. Route error buttons use Next.js 16.3's `retry` to refetch data. An isolated production Chromium test reproduced the reported decoding crash before this change and verified one automatic document reload afterward, the retry limit, manual recovery and responsive fallback layout. Normal compressed responses on the supplied production host decoded successfully in unauthenticated probes; the original transport corruption and authenticated long-idle behavior remain unverified.

Run `corepack pnpm benchmark:web` for a local synthetic benchmark with 100,000 members, 250 mapped roles and 1,000 concurrent consumers. It measures indexing, searching, grouping and database fan-out without credentials or external requests. Results depend on local CPU load; this is not a production HTTP capacity test.

Reference local run on 2026-09-30: index construction 36.81 ms, search 38.38 ms, role grouping 9.83 ms, concurrent read coalescing 0.27 ms and listener fan-out 1.33 ms. The 1,000 consumers produced one upstream read and one upstream listener. All 144 workspace tests, typecheck, lint and production build passed. A local production HTTP smoke check covered the server pages, all Voice tabs and access control without a session; protected pages redirected and all five member endpoints returned 401. Authenticated production latency and browser interaction remain unmeasured.

Navigation prefetches the route shell on hover, keyboard focus or touch using Next.js automatic prefetching. It does not force every dynamic page's database reads to run before a click. Dynamic and prefetched page segments remain in the browser router cache for 30 seconds. Live events and server-action revalidation refresh the dashboard. The dashboard shell, module headings and tabs render independently of private reads. Session profile and guild sidebar have their own Suspense boundaries, so they do not hold back the page shell. Each private data component and backend operation checks authorization before accessing data.

The guild rail and mobile picker share the server-loaded, authorized `/servers` presentation model. `manageableGuildList` now uses React request-scoped caching, so the rail and server cards reuse the same discovery, installation batches and permission resolution in one render. No icon triggers a Discord or Firestore request; installed-state documents retain their existing `getAll` batches of up to 100 IDs. Existing per-guild permission-mapping and role membership checks remain unchanged. Entering the dashboard directly on a guild page now also loads discovery for the persistent rail through its own Suspense boundary; this is an additional initial guild-list load, not a new authorization dependency for the page. The rail lives in `/servers/layout.tsx`, and the contextual sidebar lives in `/servers/[guildId]/layout.tsx`, so ordinary module transitions reuse both mounted layouts. A full reload, explicit refresh or revalidation can load discovery again. The targeted page guard still does not call the OAuth guild-list endpoint.

Discord roles and channels use the existing guild/resource-revision caches. Displayed member profiles are cached for 60 seconds, keyed by guild, member and directory revision. These caches serve presentation only. Ownership, membership and access mappings used by mutations remain live. Concurrent Firestore reads share an in-flight request and discard the result after completion; no permission decision is cached across requests.

Per-guild navigation no longer calls either OAuth `GET /users/@me/guilds` or `GET /users/@me/guilds/{guildId}/member`. Fetching the complete guild list on every tab, hover prefetch and subscription consumed the same OAuth route quota and made unrelated page transitions wait. After validating the encrypted login session, the guard starts live bot `GET /guilds/{guildId}` (including ownership), `GET /guilds/{guildId}/members/{sessionUserId}`, the installed-guild document and access mappings together. It checks the guild and member IDs before granting access, including for owners and personal grants. Results are shared only within the request. The access-control page reuses the verified live guild and mappings instead of fetching both again. `/servers` still uses the OAuth guild list for discovery and skips individual member requests when direct or `@everyone` access is sufficient. Revoked membership, transferred ownership, revoked roles and upstream failures never fall back to cached permission facts.

Activity module status, summary, individual rankings and game tables stream through independent Suspense boundaries. Member and game details also separate metadata from statistics and tables. Settings forms, Voice data pages and the server list expose their shell while guarded data loads; forms render only with their actual authoritative values. Loading counters use skeletons instead of fabricated zero values. Settings reads are shared within the request. Member profiles batch only IDs from rankings that are already ready, deduplicate shared members within that render request, and never wait for every ranking to finish. Game metadata and player queries run together; player counts use one grouping pass. The Messages page reads one 30-day daily range for all three recent counters and a server-side `sum(messages)` for the all-time counter, rather than downloading the all-time member collection and three overlapping daily ranges. The all-time sum uses one indexed field, so it does not require a new composite index or change sparse-counter semantics.

Server-streaming regression tests use React's actual pipeable renderer and delayed service promises. They verify that dashboard/page shells arrive before session/sidebar data, that Activity tabs arrive before module settings, and that summary and chat ranking chunks arrive while other rankings, games and settings are still pending. They also verify that the settings form arrives before tracker health, and that independently rendered settings and tracker components deny private reads without authorization. This verifies server chunk ordering, not authenticated production browser latency.

Run `corepack pnpm profile:web` with the existing server environment for read-only live Discord/Firestore timing. It selects a currently installed guild, skips stale installation records, prints operation durations without tokens or member/guild identifiers, and performs no writes. A 2026-10-02 local run measured the parallel live guard dependencies at 319 ms, Voice records at 171 ms, the Activity overview queries at 258 ms and all four message counters at 118 ms. These are upstream measurements, not authenticated browser/production HTTP latency or a page-speed guarantee. The browser tool could not start, so authenticated end-to-end timing remains unverified.

Member snapshots fetch at most one page when the client requests it, with 1,000 Discord members per page. Client cancellation stops further pages. The server member-page cache is bounded to 80 pages and 32 distinct pending loads, with a 120-second TTL and keys including bot credential fingerprint, guild, directory revision and cursor. Concurrent consumers of the same page share one Discord call. A changed revision selects a new cache entry.

The client displays pages progressively, batches updates, deduplicates member IDs and replays contiguous live changes received during loading. Missing revisions or reset events trigger a bounded retry with backoff. Search works while the first pages arrive and retains only the best 30 matches. A normalized search index is reused between keystrokes. Role grouping uses role ranks instead of scanning every mapped role for each member.

Visible member directories check their revision every five minutes and only reload when needed, with a full reconciliation at least every 15 minutes to cover missed Gateway events. Hidden tabs close their event connections; reconnects use backoff and jitter. Firestore listeners are shared per database and document/query, including overlapping dashboard and member streams. The last subscriber releases its listener and retained snapshot. Slow SSE clients disconnect before their event queue exceeds 64 KiB.

Discord requests have bounded queues (512 requests in total, 64 on one route), a 10-second queue timeout, a 30-second total request budget and an eight-second network timeout per attempt. Interactive ownership/member checks take precedence over queued presentation-profile reads; an interactive consumer also promotes an identical pending read. Every fifth slot is available to normal work to prevent starvation. Active requests remain serialized and Discord cooldowns are honored. A timed-out waiter cannot let later requests overtake the active request. `benchmark:web` exercises the actual scheduler with eight simulated 30 ms profile reads and compares FIFO versus interactive-check latency; this is a contention benchmark, not live HTTP timing.

Memory caches, listener sharing and request coalescing operate within each process. Multiple Railway replicas each maintain their own instances. Real capacity and first-load latency still depend on Discord/Firebase latency, API quotas, replica count, memory and CPU; measure authenticated production traffic before promising a concurrent-user limit.
