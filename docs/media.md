# Медіа v1

Media is a guild module alongside Temporary Voice and Activity. `/servers/{guildId}/media` is the player; history, settings, sources and diagnostics are separate tabs. There is one Discord audio connection per guild. No microphone audio is received or stored.

## Ownership and control plane

Browser → authenticated Next.js Media API (session-derived identity, strict request and origin validation) → authenticated bot HTTP endpoint → live membership/`PermissionService`/shared Media policy → `MediaCommandService` → `MediaSessionService` → `MediaPlaybackEngine` → Discord Voice. Pages and direct Firestore history reads additionally use `requireGuildAccess`; worker operations have one live authorization boundary in the bot rather than duplicating Discord/Firestore reads in web.

`packages/media` owns providers, safe audio HTTP and the deterministic queue scheduler. `packages/permissions` owns pure control policy; `packages/validation` owns schemas; `packages/shared` owns public metadata/session types; `packages/database` owns Firestore. Gateway and audio live in `apps/bot`. Web never imports bot runtime or handles audio. Media uses the existing VoiceStateUpdate and ChannelDelete dispatchers, including deletion by TempVoice.

`POST /internal/media` requires an independent bearer secret with at least 32 characters and accepts only validated state/search/settings/semantic-command requests. The endpoint caps bodies at 64 KiB, limits concurrent requests and throttles per guild/actor/operation. Unknown paths and unauthenticated requests fail closed. All commands fetch live Discord membership/roles and re-read current Gateway voice location. Actor IDs in browser payloads are rejected; the web derives them from the authenticated session. Web mutations enforce origin and JSON content type. Public bot endpoints require HTTPS in web configuration; private Railway and loopback HTTP origins are supported. The endpoint carries no bot/OAuth token or provider credentials in responses.

## Permissions and precedence

Runtime diagnostics are available only to authenticated Discord user `1409339485904306200`, with the same check on the web API and the bearer-protected worker endpoint. The shared logger keeps structured, sanitized entries only in each process's memory (5000 entries / 8 MiB); it does not write these logs to Firestore. Cursor polling includes the process run ID, so a worker restart starts a new journal. The right diagnostics dock is part of the dashboard layout, shrinks the workspace with an animated transition, and keeps the main controls usable. Closing it pauses polling while retaining entries, filters and scroll position; navigating between dashboard pages preserves the mounted journal. Export downloads the filtered records as JSONL.

Playback logs include source preparation, command/checkpoint transitions, resource identities, Voice/player states, decoder exit codes and sanitized stderr. A failed active stream or a known-duration stream ending more than five seconds early interrupts playback and preserves the selected track instead of silently starting another song. Natural completion still advances normally. Paused/backpressured input suspends the HTTP stalled-read timeout until reading resumes. Worker availability errors distinguish recovery, another process holding the guild lease, and failed/expired ownership confirmation without weakening the command gate.

HTTP completion can detach a response's socket before FFmpeg and Discord finish consuming buffered audio. Read-timeout changes from pipeline backpressure, pause and resume now apply only to a live socket on an unfinished response; timeout listeners are removed on response end or close. This preserves decoded playback after the download finishes instead of throwing from Node's `IncomingMessage.setTimeout`. Nested error causes and aggregate network codes are included in bounded, sanitized messages. Fatal exceptions include their stack in the hosted message field, and shutdown records identify the signal/failure reason and exit code.

A regression using a real Node `IncomingMessage` reproduced the same exception before the fix and passes afterward; another checks destroyed sockets while existing tests retain backpressure timeouts. Workspace typecheck, lint and production builds passed, along with 217 bot, 106 Media, 489 web and 21 shared tests (833 total). Deployment and audible Discord playback were not performed in this verification.

The audio player tolerates 150 missing 20-ms frames (three seconds) instead of the library's five-frame default. Idle is considered natural completion only after decoded EOF, never merely because the player destroyed its resource. Starvation, empty buffering and unexpected decoder termination preserve the selected track, including tracks with unknown duration. Diagnostics record missing frames, played duration, source completion, received bytes, HTTP status/MIME/length and intentional versus unexpected process termination. Transport request IDs associate opened streams with their queue item without retaining source URLs. Startup probes log executable versions, exit status, platform and Node version; extractor attempts include bounded sanitized warnings/stderr, timeout/cancellation and retry details. Web and bot control-plane logs share a validated request UUID, so hosted network timeouts can be distinguished from worker or provider failures. No request body, bearer secret, signed URL or extractor stdout is logged.

Hosted-playback verification on 2026-10-10: workspace typecheck, lint and production builds passed; 215 bot, 106 Media, 489 web and 19 shared tests passed. Regressions cover destroyed-but-unfinished resources, empty buffering, unknown-duration interruption, unexpected SIGKILL, preservation of buffered bytes, IPv4 preference with unchanged SSRF checks, DNS timer cleanup, extractor timeouts/startup failures, credential redaction and authenticated web/worker request correlation. The web suite passed with two workers after an unrelated lazy artwork-dialog timeout during concurrent checks. A local public YouTube Music URL probe resolved `G63iPGvgGYs` and read 16 KiB from HTTP 200 `audio/webm` using IPv4. This confirms local extraction/transport, not hosted network access or audible Discord output. After rolling out bot and web, export the current run's JSONL after a failed URL search/playback to identify any remaining hosting-specific refusal.

`media.view`: player, search and history. `media.request`: ordinary queue requests and configured same-Voice actions. `media.control` or a configured DJ role: broader playback controls. `media.manage`: module settings and administration. Existing SCRT owner/SUPER_ADMIN/ADMIN mappings grant management; VIEWER now also grants `media.request` so regular guild members can participate. This is intentional: they remain unable to change settings, remote-admin policy, volume or other unrestricted controls by default.

All controllers, including DJs, must be in the session Voice. `media.manage` bypasses location for ordinary controls only when `allowRemoteAdminControl` is enabled; default false. Starting audio always needs an eligible Voice. Ordinary users restore in the original Voice; a manager can explicitly choose “Відновити тут” to move a saved queue into their current eligible Voice and start it, including after the original temporary channel was deleted. Restoration rechecks live location and effective ViewChannel/Connect/Speak before joining. `MOVE_SESSION` requires media.manage, current presence in the target channel and the same effective permissions. Moving an active session restarts the current track from the beginning, preserves the queue and explains the behavior in a confirmation dialog.

Control modes OPEN/QUEUE/DJ and `sameVoiceUsersCan` configure ordinary actions. Defaults permit requests, pause/resume and own removal/reordering, with stronger actions reserved for DJ/manage. Own reordering cannot cross another requester's items. Session locks take precedence: DJ lock restricts controls while allowing configured requests; admin lock requires media.manage. DJs cannot set an admin lock.

Default skip mode is vote, ratio 0.5 rounded up, minimum one. Count all currently connected humans, including deafened users; ignore bots. Votes live in runtime and are tied to the current queue item. Leaving removes a vote; listener join/leave recalculates the threshold. Track, lock and settings changes clear votes. DJ/manage can directly skip. DJ/admin locks also restrict voting; remote administrators cannot vote on behalf of listeners.

## Sources

| Provider | Search | Metadata | Playback | Live | Seek |
| --- | --- | --- | --- | --- | --- |
| Direct HTTP audio | Exact URL | Filename/host + audio headers | Yes | ICY headers | No |
| YouTube / YouTube Music | yt-dlp, track URL or title/artist | Video/channel/artwork/duration | Public HTTP audio | No | Finite tracks |

YouTube and SoundCloud use a pinned official yt-dlp standalone build installed automatically by bot dev/build scripts (Windows x64, Linux x64/arm64 and macOS). No provider API key is needed for this audio path. Public, non-age-gated HTTP audio is supported, including finite, unencrypted SoundCloud HLS audio. SoundCloud falls back to native HLS when progressive audio is unavailable, including its `playback.media-streaming.soundcloud.cloud` CDN. The worker validates a bounded media manifest, streams its initialization segment and audio segments in order through the DNS-pinned transport, and cancels pending segment requests when playback is replaced or stopped. Every segment redirect retains the provider CDN allowlist; FFmpeg still receives bytes over stdin only. Live/master playlists, encryption, byte ranges and discontinuities are rejected. Private/authenticated content and access restrictions are not bypassed. Public SoundCloud playlists are browsed separately as described below. A source may refuse requests from a hosting IP or demand authentication. Those failures are reported explicitly; a working extractor does not guarantee every upstream track is accessible. Source URLs are routed to their provider and cannot masquerade as direct playable audio.

Extraction repeats the same public request at most once after a transient network failure, within the original 20-second deadline. Cancellation interrupts the retry delay, and the four-process concurrency limit includes retries. Login requirements, private/removed tracks, explicit rate limits, bot-verification refusals and unsupported formats are not retried immediately. Bot verification produces `NETWORK_BLOCKED`, marks only that provider degraded and pauses new extraction for 60 seconds without extending the pause on additional clicks; valid cached audio and other providers remain usable. Missing outbound routes produce `NETWORK_UNREACHABLE`. Generic unavailable replies are not assumed to mean a private/deleted track; explicit YouTube session throttling is reported as a temporary network restriction. Temporary CDN HTTP 408/5xx or EAI_AGAIN/ECONNRESET/ETIMEDOUT failures retry the same validated stream opening once after 500 ms, respecting playback cancellation. Concurrent catalog lookups for alternate share URLs of the same track share one extraction; playback cancellation stays independent. Network refusals are distinguished from a track requiring authentication, and raw extractor errors or signed stream URLs never reach the dashboard.

The executable runs without a shell, local configuration or plugins and receives only canonical provider URLs or bounded provider search expressions. Child environments omit SCRT credentials. Each extraction has a 20-second timeout, a 2-MB JSON limit, socket/retry bounds and a four-process concurrency limit. Signed CDN URLs and upstream headers remain transient in a bounded 128-entry worker cache for at most five minutes, expiring a minute before the upstream `expire` timestamp when present; queue/history and responses store only canonical track references. Search → selection → playback can reuse a recently inspected public audio resource. Expired entries are extracted again; failed stream opens invalidate the entry. A cached signature rejected with HTTP 401/403/410 receives one fresh extraction and stream open under the original cancellation signal. Persistent refusals stop without a retry loop. Every playback open still passes the DNS-pinned, SSRF-protected HTTP transport and provider CDN allowlist. FFmpeg receives bytes over stdin only.

Search uses explicit submission, bounded provider fanout, in-flight coalescing, a 128-query/page, 2-minute runtime cache and bounded responses. «Завантажити ще» requests a validated page from 0 to 9 and appends distinct canonical track identities, up to 200 in the player. Online audio searches return up to 20 flat catalog entries per provider/page (40 total), with bounded artwork metadata and without inspecting each audio stream. Catalog-only URLs never enter the signed-audio cache: playback resolves and verifies the selected song before acknowledging success. Search extraction has an eight-second budget, with at most two concurrent searches so playback retains extractor capacity. SoundCloud reuses yt-dlp's public client discovery cache under the ignored `.media-tools/soundcloud-cache/` directory; no user credentials or audio links are stored there. Exact track URLs retain full inspection and have no further page. Catalog 429 responses respect Retry-After with a bounded cooldown. Outages are isolated by provider. Optional credentials never prevent bot startup. Health reports configuration and recent failures; it is not a continuous upstream availability probe.

Text queries normalize pasted whitespace and Unicode. Results rank by title/artist token coverage, including accents, Ukrainian transliteration, short edit distances and adjacent transpositions. Implausible keyboard layouts are corrected before searching; weak first-page results get at most one optional fallback using previously searched public vocabulary (unambiguous edits or a clearly more frequent artist/title spelling) or a broader artist/title query. Corrections reuse already cached successful searches. The first page can additionally include up to 12 closely matching public tracks from recent searches, within the 40-result response limit, preserving native exact matches and current provider availability. Pagination retains the chosen upstream query for two minutes, avoiding a different correction on each page. The UI shows `matchedQuery` when an alternative was used. A failed fallback preserves original matches and logs its reason; if no original matches exist, the source failure remains visible. Malformed entries are logged and skipped; an entirely malformed response reports a source error rather than a false empty search. This is bounded fuzzy matching, not a guarantee for arbitrary misspellings or unavailable catalog content. The browser caches successful searches for two minutes within its user/guild/provider scope and lets a different query cancel an older request; failures and late aborted replies are never cached.

Search verification (2026-10-11): a local production-mode registry returned 20 SoundCloud tracks for `Linkin Park Numb` in 2.66 seconds and reused the exact result in under one millisecond. After that catalog search, `Linkn Park Nubm` resolved to the same canonical query and 20 results in 2.14 seconds; the wrong-layout query `дштлшт зфкл тгьи` reused them in four milliseconds. Another uncached page returned 20 tracks; observed provider latency varied and these measurements are not Railway latency guarantees. A separate development YouTube search returned 20 valid entries in 1.88 seconds. No bot login, Discord playback or Railway deployment was performed for this search verification.

YouTube Music `watch?v=...`, YouTube watch/short/live/embed and youtu.be URLs normalize to one video ID, ignoring share/playlist parameters. SoundCloud track URLs normalize to their public path. The optional YouTube Data API remains a metadata-only fallback when the audio extractor is unavailable. Search results distinguish playable tracks from metadata and report source/access failures instead of false empty matches.

Direct URLs are limited to HTTP/HTTPS on normal ports without credentials, fragments or query parameters. Validate literals and all DNS answers against public address ranges; reject loopback, private, link-local, metadata, reserved IPv4, private/mapped IPv6 and special transition ranges. Each connection pins the validated DNS result and preserves the hostname for TLS verification. Every redirect is independently checked, with at most three redirects, a DNS deadline, an 8-second header timeout and a 15-second stalled-read timeout. Only recognized audio MIME types are accepted; HTML/HLS/playlists are rejected. Search/resolve checks headers and closes the stream without downloading the file. Playback opens a new validated stream.

Provider extraction uses IPv4, and the safe HTTP transport prefers a public IPv4 DNS answer when available to avoid unusable IPv6 routes on hosting networks. IPv6-only direct audio remains supported; all DNS answers must still be public, including addresses not chosen for the connection. DNS deadline timers are cleared after resolution. These network choices do not weaken DNS pinning, redirect validation or TLS hostname checks.

FFmpeg receives **stdin only**, with `-protocol_whitelist pipe`; user URLs are never FFmpeg arguments. Audio files with unknown duration are capped at the configured maximum decoded duration. Recognized live streams require explicit guild opt-in. Only canonical public references reach queue/history; private query tokens are rejected. Do not place secrets in artwork or public source URLs.

## Queue, progress and persistence

Guild settings include `inactivityDisconnectSeconds` (integer 0–3600, default 300 for existing and new documents; 0 disables it). A connected bot leaves after continuous paused/idle time, including an exhausted queue even with listeners present. Playback cancels the timer. Updating the setting recalculates the deadline from the existing idle start; polling and unrelated commands do not extend it. Disconnect preserves the paused track at the front of the queue for explicit recovery from its beginning. The existing empty-channel grace remains independent; whichever deadline comes first disconnects. Timers are process-local, serialized with guild commands, cancelled on shutdown/lease loss, and never persisted or polled through Firestore. The timeout and reason are included in runtime logs.

Queue metadata is embedded in `mediaState/current` so queue/current/revision updates are atomic; maximum 100 total pending/current items bounds the active queue. `played` retains the last 100 distinct completed/skipped tracks, independently of request limits, across navigation, stop and worker restart. Old documents default to an empty retained list. The player shows current, upcoming and played sections; played covers replay through the same authorized command, with a fresh queue identity to reject old engine events. Own-item removal policy applies to retained entries; reordering applies only to upcoming entries. Repeat does not accumulate duplicate retained rows. FIFO and requester round-robin preserve metadata. Fair scheduling starts after the last requester; shuffle randomizes stored upcoming order and repeat controls track/queue end behavior. Failed items never repeat. Runtime transitions make at most three failed-source attempts within a 45-second deadline before preserving the remaining queue for explicit recovery.

Every browser/slash command carries commandId, guildId, actorUserId, sessionId and expectedQueueVersion. A per-guild serial executor and Firestore revision transaction reject conflicts. Durable receipts make identical retries safe; changing the payload with an existing ID is rejected. Version checks apply to controls as well as queue edits, so stale double skip cannot skip a newly started track. Intent is persisted before initial playback. Audible effects and Firestore cannot form one transaction; crash recovery conservatively treats prior audio as interrupted.

The player offers ▶ on search/queue artwork for `PLAY_TRACK` and a separate + action to append. Selecting a queued track preserves its original requester and the other queued tracks; explicit selection takes priority over fair scheduling for that transition. Replacing the current track requires direct-skip/DJ/manage policy and cannot bypass voting, Voice location or session locks. A new session can start under normal request policy. Queue arrows and drag-and-drop preserve backend own-item/fair-mode restrictions.

Finite public YouTube/SoundCloud tracks with known duration expose a seek slider. Dragging or clicking previews a position and sends one `SEEK` on release; arrow/Home/End keys also work. Seeking uses the direct-skip/DJ/manage policy so it cannot bypass vote-only skipping. Requests include the current queue identity and the normal session/version guards. Live streams, unknown-duration audio, direct HTTP and metadata-only tracks retain read-only progress. Positions must precede the track end and remain within the guild duration limit.

The worker resolves and opens validated audio again, then prepares a second decoder with FFmpeg output `-ss` on stdin bytes. Decoder readiness has a 15-second deadline; large offsets can therefore be refused safely. Current audio continues until the new resource is readable and Voice/ownership checks pass again. Preparation failure disposes only the new stream. A successful seek preserves pause, volume, requester, queue and retained tracks, clears votes, rotates the current resource identity and stores a playback offset with a new segment timestamp. Old end/error events cannot advance the new position. Legacy sessions without an offset use zero; normal playback/recovery resets it.

Playing a search cover includes canonical references for the following loaded, playable results in the current source filter, at most 99. The worker obtains their public metadata from a bounded 512-track/24-hour search cache or persisted retained entries, deduplicates identities, skips prohibited tracks, respects live guild/per-requester limits and appends after existing manual requests. After a worker restart, cache misses resolve through the actual source in a fanout of at most four with a 15-second preparation budget and cancellation. Preparation failures report a safe error before interrupting current audio; browser metadata never authorizes a track. The whole accepted continuation is checkpointed once before playback, so advancing does not depend on an open browser or add one request/write per search result. Source restrictions are refreshed before each audio start; metadata never authorizes a stale/restricted stream. Submitted queues survive restart and use normal explicit recovery.

The player derives its accent from the current cover's dominant chromatic region. A darker tint creates a stronger radial glow around the artwork, fading into the normal surface toward the controls; readable controls retain the lighter accent. A decoded cover overlays the previous cover with a 1.6-second fade while a registered CSS color property interpolates the accent. Previous visible layers remain until the newer one is opaque, including rapid track changes. A 64-cover client cache avoids repeated palette work. YouTube's equivalent JPEG is used where WebP lacks canvas CORS access; other inaccessible artwork keeps a neutral accent and a normally loaded cover. Reduced-motion preferences disable the animation.

Search drafts, completed results (maximum 200), next page, source filter and mobile panel survive page navigation in validated sessionStorage scoped by authenticated user and guild. They expire after 24 hours; disabled storage falls back to normal page behavior. Authorization, pending commands and live session state are never restored from that cache. The last confirmed guild volume remains in `mediaState/current` and is reused for a new playback session, including after a worker restart, clamped to the current guild volume limit.

Pause/resume, volume, repeat, locks and queue edits update the client immediately. An ordered local command stream accepts further clicks while a request is pending and dispatches them with the latest acknowledged session/queue version. Adjacent unstarted track selections coalesce to the latest choice, while the in-flight command remains ordered. Each successful command returns a validated public snapshot, removing state preflight and follow-up GET requests. A rejected/uncertain command rolls back optimistic state, cancels its dependent queued actions and reconciles once. A definite PLAY_TRACK preparation rejection (422) preserves newer selections after reconciliation; one 409 queue-version conflict can rebase within the same session. Unknown outcomes are never blindly retried. Old polls cannot overwrite command acknowledgments. Discord permission checks and Firestore revision/receipt checks still run for every command; audio startup remains subject to upstream network and decoding time.

Manual PLAY_TRACK first opens the selected source and prepares actual decoded Opus packets while current audio remains installed. Before replacing audio, the worker rechecks Gateway voice location, permission policy, channel eligibility, guild ownership and listeners, then checkpoints the selected identity and command receipt. The engine swaps the prepared resource and verifies the Playing state before returning the confirmed snapshot. Preparation failure keeps the current session, queue and history intact and returns 422; manual selection never falls through to another queued track. Persistence or post-commit failures stop the runtime and recover the saved intent. Automatic queue advancement retains its bounded failure-skipping policy. The player keeps the confirmed title, cover and progress during preparation and displays a separate pending-selection status.

Ordinary successful controls use the existing synchronization indicator, without a persistent generic success banner. Add/vote acknowledgments appear in a small fixed toast and dismiss after 3.2 seconds without shifting the page. Errors and explicit recovery instructions remain visible until dismissed or the next action.

Progress is interpolated from bot timestamps once per second in a focused client component. State uses non-overlapping 5-second polling only while visible; each poll reauthorizes access and includes runtime listeners/votes. This was chosen over a new cross-process SSE/WebSocket transport to retain a bounded, auditable deployment footprint. Firestore is written at semantic transitions, not for progress or presentation-only listener changes. A separate 60-second ownership lease renews every 30 seconds per installed guild; this is coordination, not a playback clock. Keep **one bot replica**. The lease protects rollout overlap and failed renewal revokes control and stops playback.

## Production search and shared favorites

With `NODE_ENV=production`, the bot excludes YouTube from text search and returns an explicit disabled-source message for YouTube links, without invoking its extractor. SoundCloud search and direct audio URLs remain available. Development still offers YouTube. The web also removes cached YouTube search results and hides its search filter and favorites in production; existing saved tracks are retained. This is a temporary source restriction, not a claim that the hosted YouTube network block has been resolved.

Hearts in the player, search, queue and history save a canonical public track and the signed-in user's ID/name in the current guild's favorites. The web rechecks live guild membership and `media.view` before every list or mutation, derives identity from the session, and asks the bot for trusted metadata when adding a heart. No client-provided track metadata, liker ID, stream URL or credentials are accepted. Firestore transactions preserve other users' hearts, repeated desired-state writes are idempotent, and removing the final heart deletes the track's favorite document. Removing a heart does not require the media worker to be available.

The persistent dashboard context loads favorites for the authorized selected guild in pages of 50, using the document-ID index; no extra composite index is needed. Its loaded collection and hearts survive tab navigation. The Favorites tab shows each track once, with all likers, plus filters for everyone, the signed-in user, another liker, and title/artist. Refresh fetches other users' changes on demand. The favorites collection persists between deployments; runtime diagnostic logs remain session-only.

`PLAY_FAVORITES` accepts an ordered list of 1–100 unique favorite IDs, reads only the current guild's documents, and applies the same live Voice/DJ/lock policy as `PLAY_TRACK`. It prepares and confirms the selected first track before replacing audio, then retains every remaining favorite without duplicates. All tracks must fit the configured queue/per-user limits; a missing track or oversized collection is rejected before changing playback, with a visible explanation rather than silent truncation. Later tracks refresh their provider resource when playback reaches them. The current song and queue remain intact if a favorites read or initial preparation fails.

## Lifecycle and recovery

States: idle, connecting, buffering, playing, paused, reconnecting, stopping, error. Connections use @discordjs/voice readiness/reconnect lifecycle with bounded recovery; engine errors and expired/failed active resources interrupt playback and preserve the selected track for explicit recovery. Errors never retry a broken resource indefinitely. Permanent disconnect/channel deletion preserves the interrupted track at the front for recovery. Manual moves update actual Voice identity only if the target is eligible; invalid targets interrupt safely.

Empty channel default: pause, wait 120 seconds, leave if still empty, preserve queue. Rejoining cancels the timer and leaves playback paused unless resumeOnRejoin is explicitly enabled. The stop-then-leave alternative saves the interrupted track for a fresh restart. A stream is not started when the channel has no human listeners.

SIGTERM/SIGINT checkpoint queue/current identity, stop FFmpeg and destroy Voice within the existing bot shutdown deadline. On startup any persisted active audio is interrupted, current track returns to the front, session identity rotates, and audio never auto-plays. Authorized users in the original Voice choose **Відновити**. Media engine import/dependency/startup errors degrade Media while Activity and TempVoice remain available.

## Player conveniences and wide displays

The player previews the next scheduled track, or the current track when repeat applies. Artist discovery submits the displayed artist immediately and focuses the catalog search; later responses preserve any newly edited draft. The source link opens the track's public provider page. The queue filter matches title, artist and requester across upcoming and retained tracks. Filtered rows keep their original queue positions and move boundaries; drag reordering is available only with the filter cleared. Played tracks are collapsed until expanded, and upcoming duration uses hours for long queues and labels incomplete durations as a lower bound.

Space toggles playback, physical J/L keys seek by ten seconds on supported tracks, and `/` focuses search. Shortcuts use existing controller permissions and pause while commands are pending. They ignore text entry, interactive controls, open dialogs, composing text, Ctrl/Alt/Meta combinations and held keys. The decorative playback indicator animates only while audio is playing; new transitions respect reduced motion.

At widths of at least 1900px and an aspect ratio of at least 2:1, the player becomes a vertical deck beside the catalog and queue. The centered workspace has a 2800px limit, bounded list heights and independent scrolling, with artwork sized to available screen height. Wide catalog panels display two columns of cards. Standard displays retain a horizontal player; phones retain separate search/queue tabs.

## Setup

1. Update the bot install permissions to include **Speak**, plus ViewChannel and Connect, and check effective channel/category overwrites. No Administrator, MessageContent or new privileged intent is required by Media. `/media` replies are ephemeral; existing core message permissions remain centralized.
2. Use Node >=22.12 for pinned @discordjs/voice 0.19.2, installed `opusscript` and the bundled DAVE library. Install FFmpeg on PATH, or set MEDIA_FFMPEG_PATH to a server executable path. Dependency health is checked at startup; missing FFmpeg degrades Media.
3. Bot and web: set the **same independent random MEDIA_INTERNAL_SECRET** (at least 32 characters; different from SESSION_SECRET). Locally set bot host 127.0.0.1, port 3100, and web MEDIA_BOT_URL=http://127.0.0.1:3100.
4. Railway bot: set MEDIA_INTERNAL_HOST=::, MEDIA_INTERNAL_PORT=3100 and RAILPACK_CONFIG_FILE=railpack.bot.json. The bot-specific config retains generated runtime packages and adds FFmpeg. Web on the same Railway project: MEDIA_BOT_URL=http://<bot-service>.railway.internal:3100. Web outside that private network needs an HTTPS bot domain pointing to port 3100. Configure only one persistent bot replica. The HTTP port is an authenticated control plane, not a keepalive.
5. Bot-only optional YouTube metadata fallback: YOUTUBE_API_KEY. Public YouTube/SoundCloud audio uses the extractor without new provider keys. No provider key belongs in NEXT_PUBLIC_* or browser code.
6. Deploy Firestore index/TTL configuration. Register `/media` with `pnpm deploy:commands` in the intended environment. Enable the module through Media settings; choose DJ roles, Voice allow/deny lists or categories, queue policy and remote-admin behavior.

For hosted YouTube failures containing “Sign in to confirm you're not a bot”, [yt-dlp's known-issues guidance](https://github.com/yt-dlp/yt-dlp/issues/3766) identifies a blocked logged-out IP. Repeating the request or adding a metadata API key does not change the outbound address. Playback remains on the selected track and reports the refusal rather than claiming success or substituting another song.

Bot-only `MEDIA_YOUTUBE_IP_FAMILY` accepts `ipv4` (default) or `ipv6`. It selects the family for both YouTube extraction/search and the signed audio transport, including redirects. IPv6 mode requires an IPv6 DNS answer and route; it never silently falls back to IPv4. SoundCloud and direct audio keep their existing routing. Both modes retain public-address validation, DNS pinning and TLS hostname verification. Startup records `youtubeIpFamily`; extractor and transport records include their actual `family`. The dependency diagnostic reports this configuration but does not verify upstream acceptance.

If the hosted network is still refused, set bot-only `MEDIA_YOUTUBE_PROXY_URL` to an operator-controlled HTTP(S) CONNECT proxy origin, for example `http://<username>:<password>@<host>:<port>`. Percent-encode reserved characters in credentials. Configure it only in bot server variables; it is excluded from the web environment schema and never stored in Firestore or browser state. The proxy must have a stable public outbound address that YouTube accepts, and must permit CONNECT to public IP destinations. Changing this variable requires restarting the bot. Empty/unset retains direct routing. Proxy mode overrides direct `MEDIA_YOUTUBE_IP_FAMILY` selection and uses IPv4 to reach the proxy and to pin each audio destination; SoundCloud and direct audio retain their normal routing.

YouTube inspection/search and audio bytes use the same proxy, including audio redirects. This avoids extracting an IP-bound media URL on one connection and downloading it from another, as described in [yt-dlp's FAQ](https://github.com/yt-dlp/yt-dlp/wiki/FAQ#i-extracted-a-video-url-but-it-does-not-play-on-another-machine--in-my-web-browser). Audio still validates every destination and DNS answer before CONNECT; the proxy receives the pinned public IP, while the origin Host header and TLS hostname verification are retained. Proxy credentials are confined to the proxy handshake, omitted from origin requests, and removed from extractor stderr and dependency debug URLs. CONNECT has an eight-second deadline and obeys playback cancellation; subsequent audio retains its existing stalled-read timeout. There is no silent fallback to Railway if the proxy fails. Use one stable route rather than rotating proxies because playback and extraction must use the same outbound address.

Startup reports `youtubeRoute`; extractor and HTTP events report `route: direct|proxy`, plus their address family. `PROXY_AUTH_REQUIRED` identifies rejected proxy credentials. Missing routing or an unavailable proxy produces `NETWORK_UNREACHABLE`; an upstream bot-verification refusal remains `NETWORK_BLOCKED`. Automatic queue advancement interrupts and preserves the attempted track and following queue on these provider-wide failures instead of marking songs failed and switching to another source. A genuinely unavailable individual track retains the existing bounded skip behavior.

Test a previously rejected YouTube URL after rollout. Choosing IPv6 does not guarantee YouTube accepts that address. A further `NETWORK_BLOCKED` requires reviewing the current run's logs and using a network address accepted by the source; `NETWORK_UNREACHABLE` indicates the outbound route needs checking. To restore the original YouTube routing, set `MEDIA_YOUTUBE_IP_FAMILY=ipv4` and redeploy. Repository changes do not enable the Railway setting themselves.

## SoundCloud playlists

Paste a public SoundCloud `/artist/sets/name` link into the player search to get a playlist card. Opening the card only reads its catalog; it never joins Voice or starts playback. The accessible preview shows the artwork, owner, original track positions, availability and durations, loads 50 tracks at a time (up to 500), and filters the loaded tracks. Individual play/add buttons act on just that track. Opening, closing and navigating between favorites tabs preserves the main player and favorite collection state.

`PLAY_PLAYLIST` is a single authenticated, idempotent command. The worker checks live guild membership, Voice policy and configured queue/user limits before changing playback. It obtains the entire playlist from SoundCloud, preserves original ordering or shuffles the complete selection with Fisher–Yates, and prepares the first audio source before atomically replacing the current queue. It sets queue shuffle to the requested mode and resets repeat so a previous mode cannot override the requested order. A playlist that exceeds current limits is rejected in full with an actionable message; no silent truncation. Metadata-unavailable tracks, restricted previews and tracks blocked by guild settings are skipped with a warning. A source/metadata preparation failure keeps the existing playback and queue.

Catalog data comes from SoundCloud's public set-page hydration. Missing track metadata is hydrated in one anonymous, bounded API batch per page. HTTPS requests allow only `soundcloud.com` or `api-v2.soundcloud.com`, pin validated public DNS addresses, recheck every redirect, enforce content types/body limits and a 20-second overall deadline. Public catalogs/pages are cached for two minutes with bounded maps and two concurrent page requests. Neither audio URLs, track authorization values nor user credentials enter these caches or responses. Source failures, loaded counts, page timings, skipped counts and playback mode are recorded in process-local runtime logs.

Playlist hearts use `guilds/{guildId}/mediaFavoritePlaylists/{sha256(["soundcloud", canonicalSetUrl])}`. Each record stores only the canonical public playlist header (`provider`, `providerItemId`, `title`, `artist`, `artworkUrl`, `externalUrl`, `trackCount`), `likedBy[{userId,name,likedAt}]` and `updatedAt`; it never stores the track catalog or playback URLs. The playlist-heart API applies the same live access, signed-in identity, origin and transactional like/unlike rules as track hearts. Favorites has separate Songs/Playlists views with all/my/member filtering. Playlist records load on demand in 50-document pages using the document-ID index; previews/playback fetch the current source catalog. No new compound Firestore index is required.
